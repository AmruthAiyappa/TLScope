Public Key Infrastructure & TLS Architecture

A rigorous technical reference detailing Transport Layer Security protocols, X.509 certificate trust chains, cryptographic cipher suites, and verification algorithms.

1. Core Guarantees of Transport Layer Security

Transport Layer Security (TLS) resides between the transport layer (TCP) and the application layer (HTTP/WebSocket/SMTP). It solves the fundamental network problem of untrusted intermediate routing by providing three cryptographic guarantees:

Confidentiality

Payload plaintext is encrypted using high-entropy symmetric ciphers (AES-256-GCM, ChaCha20-Poly1305), ensuring eavesdroppers observe only ciphertext.

Integrity

Authenticated Encryption with Associated Data (AEAD) ensures that any transmission bit modification or truncation is mathematically detected and dropped.

Authentication

The remote server's cryptographic identity is authenticated via X.509 digital certificates and digital signatures signed by trusted authorities.

2. Public Key Infrastructure (PKI) & Trust Chains

An X.509 digital certificate binds a cryptographic public key to a designated domain name identity. Because operating systems cannot store millions of site certificates, trust is established hierarchically:

ROOT CA Pre-Installed Root Trust Anchor

Pre-distributed in operating system and browser trust stores (e.g. Mozilla NSS, Windows Root Store). Root CAs are unconditionally trusted and strictly self-signed. Their private keys remain in air-gapped Hardware Security Modules (HSMs).

INTERMEDIATE CA Delegated Issuing Authority

Signed directly by a Root CA with the BasicConstraints: CA:TRUE, keyCertSign extensions. Intermediates issue end-entity certificates on a daily basis, insulating the root private key from compromise.

LEAF CERTIFICATE Target Server End-Entity

Presented by the target web server during the TLS handshake. Binds domain identities in the Subject Alternative Name (SAN) extension. Cannot sign other certificates (BasicConstraints: CA:FALSE).

3. Hostname Verification & RFC 6125 Standard

Having a valid, trusted certificate signature is useless if the certificate belongs to an entity other than the one intended. If an attacker intercepts traffic destined for bank.com and presents a valid certificate for attacker.com, an application without hostname verification would accept the connection.

  • RFC 6125 Mandate: Clients match the requested hostname against the Subject Alternative Name (SAN) extension entries (e.g. dNSName or iPAddress).
  • Legacy Common Name (CN): Deprecated by RFC 6125 and ignored by modern browsers when SAN extensions are present.
  • Wildcard Matching Rules: A wildcard such as *.example.com matches foo.example.com, but MUST NOT match multi-level subdomains such as bar.foo.example.com.

4. Cryptographic Ciphers & Perfect Forward Secrecy (PFS)

In modern TLS, cipher suites specify the key exchange, authentication, symmetric encryption, and integrity algorithms:

Primitive Legacy / Vulnerable (Deprecated) Modern Recommended Standards
Key Exchange Static RSA (Vulnerable: No PFS) ECDHE (P-256, X25519) with Mandatory PFS
Symmetric Cipher RC4, 3DES, CBC-mode AES (POODLE / Lucky13) AES-128-GCM, AES-256-GCM, ChaCha20-Poly1305
Signature Hash MD5, SHA-1 (Collision Attacks) SHA-256, SHA-384, SHA-512, Ed25519
What is Perfect Forward Secrecy (PFS)?

PFS ensures that session keys are generated ephemerally via Diffie-Hellman exchange rather than being encrypted under the server's long-term RSA private key. If the server's private key is stolen or leaked in the future, an adversary who recorded past network traffic cannot retrospectively decrypt the stored communications.

5. HTTP Strict Transport Security (HSTS, RFC 6797)

Even when a web server supports HTTPS, users often type example.com into their browser, triggering an initial plaintext HTTP request over port 80. An attacker on the local network can intercept this request and execute an SSL Stripping attack, preventing the upgrade to HTTPS.

HSTS (RFC 6797) prevents this vulnerability:

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
  • max-age=31536000: Instructs the browser to strictly remember to communicate only via HTTPS for at least 1 year.
  • includeSubDomains: Applies the HTTPS enforcement rule to all subdomains.
  • preload: Submits the domain to browser vendor preload lists, enforcing HTTPS on the very first connection.
